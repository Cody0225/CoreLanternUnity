# AI開発ログ → note / X 半自動パブリッシュ運用テンプレ

開発の失敗・学び・作業ログを、note記事やX投稿に「半自動」で変換するための運用メモ。
**半自動であって全自動ではない。** 公開・投稿・販売・git操作は、必ず人間が最終確認する。

最終更新: 2026-06-09

---

## 1. 目的

- Eggcore（Unity個人開発）の作業ログや失敗談を、note記事・X投稿に効率よく変換する。
- 毎回ゼロから書く負担を減らし、「下書きまではAIに任せる／公開は人間が決める」流れを定着させる。
- 記事を通じて、将来的に有料テンプレ集などの副収益導線につなげる余地を残す（保証はしない、あくまで導線）。

この運用の前提は次の一点に尽きる。

> **AIは普通にミスる。だから公開・投稿・git操作は人間が最終確認する。**

---

## 2. 基本方針

- **AIは下書き屋。編集長は自分。** 文章生成・要約・構成案まではAIに任せ、出すかどうかは人間が判断する。
- **誠実なトーンを守る。** 専門家ぶらない。収益保証を書かない。「完全に防げる」「全自動で稼げる」のような誇大表現はしない。
- **一次情報は自分の作業ログ。** AIに作り話をさせない。実際に起きたこと・自分が確認できることだけを記事にする。
- **公開は不可逆だと意識する。** 一度出した文章は拡散・キャッシュ・引用され、消しても完全には消えない。出す前に必ず読み返す。
- **小さく出して直す。** 完璧を待たず、誠実な範囲で出して、反応を見て次に活かす。

---

## 3. 自動化してよい作業

AIに任せてよい（人間レビュー前提の）作業:

- 作業ログ・メモから**記事の構成案**を作る。
- 構成案から**note下書き(Markdown)**を書く。
- 下書きの**読みやすさ・誤字・トーンのチェック**（ChatGPTレビュー）。
- 下書きから**X告知文の候補**を複数パターン出す。
- タイトル・見出し・要約の**言い換え候補**を出す。
- 公開前チェックリストの**自己点検の下書き**（最終判断は人間）。

いずれも「下書き・候補・案」の生成まで。**確定はしない。**

---

## 4. 人間が必ず確認する作業

次は、AIの出力をそのまま使わず、必ず自分の目で確認してから進める:

- **note記事の公開**（公開ボタンは人間が押す）。
- **Xへの投稿**（投稿ボタンは人間が押す）。
- **有料コンテンツの値付け・販売開始。**
- **git add / commit / push / PR作成**（差分を自分で確認してから）。
- 記事内の**事実・数値・固有名詞**（誇張や捏造がないか）。
- **他者・他サービスへの言及**（角が立つ表現、誤解を招く比較になっていないか）。
- **誇大表現・収益保証のチェック**（基本方針に反していないか）。

---

## 5. 自動化しない作業

仕組みとして「AIに任せない」と決めておくもの:

- **noteやXへの自動投稿。** APIや予約投稿で人間確認を飛ばす運用はしない。
- **公開済み記事のAIによる勝手な書き換え・再公開。**
- **販売価格の自動決定・自動値下げ。**
- **DM返信・コメント対応の自動化**（誤対応のリスクが大きい）。
- **「バズりそうだから」という理由だけの過激化・煽り。**

---

## 6. Eggcore作業ログから note 記事にする流れ

ざっくりした標準フロー。各ステップで止まれることが大事。

1. **ネタを拾う** … 作業中に「困った」「ハマった」「学んだ」が出たらメモに1〜3行で残す。
2. **ログを整理する** … 後でまとめて、時系列・原因・対処・学びの形にざっくり整える。
3. **構成案を作る（AI）** … 下のプロンプトで見出し構成を出させる。
4. **下書きを作る（AI）** … 構成案からnote下書き(Markdown)を生成。`docs/` に下書きファイルとして保存。
5. **レビューする（AI＋人間）** … ChatGPTレビュー用プロンプトで読みやすさ・誇大表現を点検 → 自分で読み返す。
6. **公開前チェック（人間）** … 第9章のチェックリストを通す。
7. **公開する（人間）** … note公開ボタンは自分で押す。
8. **告知する（人間）** … X告知文を生成 → 第11章のチェック → 自分で投稿。
9. **振り返る** … 第12章の数字を見て、第13章の基準で次のネタを決める。

> 下書きはまず `docs/` 配下にMarkdownでためてからnoteへコピペするとGit履歴に残せて安全。

## 7. note下書き作成プロンプト

作業ログを渡して下書きを作らせるテンプレ。AIに渡す例:

```text
あなたは私の下書き担当です。以下の作業ログをもとに、note記事の下書きをMarkdownで作ってください。

# 守ってほしいこと
- 専門家ぶらない。個人開発者の体験談のトーン。
- 収益保証や「完全に防げる」「全自動で稼げる」などの誇大表現を使わない。
- ログにない事実・数値を勝手に作らない。不明な点は「未確認」と書く。
- コードや画像は生成しない（必要なら「ここに図」とプレースホルダのみ）。
- 構成: はじめに / 何が起きたか / 原因 / 対処 / 学び / まとめ（必要に応じ調整可）。

# 作業ログ
（ここに自分のログを貼る）

# 出力
- note向けの読みやすいMarkdown下書き。
- 最後に「タイトル案を3つ」付けてください。
```

## 8. ChatGPTレビュー用プロンプト

下書きを点検させるテンプレ。**編集はさせず、指摘だけ**もらうのがコツ。

```text
以下のnote下書きをレビューしてください。今回は書き換えず、指摘だけ出してください。

# チェックしてほしい観点
1. 読みやすさ（長すぎる段落、分かりにくい言い回し）
2. 売り込み感が強すぎないか
3. 誇大表現・収益保証になっていないか（「完全」「必ず」「全自動」など）
4. 事実として怪しい/裏取りが要りそうな箇所
5. 他者・他サービスへの言い過ぎた表現

# 出力形式
- 指摘ごとに「該当箇所」「何が気になるか」「直す方向の案」
- 修正済み全文は出さなくてよい（自分で直すため）

# 下書き
（ここに下書きを貼る）
```

## 9. note公開前チェックリスト

公開ボタンを押す前に、人間が一つずつ確認する:

- [ ] タイトルと中身が一致している（釣りタイトルになっていない）。
- [ ] 誇大表現・収益保証がない（「完全」「必ず稼げる」等を使っていない）。
- [ ] 事実・数値・固有名詞を自分で確認した。
- [ ] 他者・他サービスへの不当な表現がない。
- [ ] 個人情報・未公開情報・APIキー等の秘密が混入していない。
- [ ] 引用・スクショの権利関係に問題がない。
- [ ] 無料記事として読んでも役に立つ内容になっている。
- [ ] 有料導線がある場合、押し売りになっていない（自然な範囲）。
- [ ] 誤字脱字・リンク切れを最終確認した。
- [ ] **公開は自分の意思で押す**（AIに急かされて押さない）。

## 10. X告知文作成プロンプト

公開したnoteを告知するX文の候補を出させるテンプレ:

```text
以下のnote記事を告知するX(Twitter)投稿文の候補を作ってください。

# 条件
- 個人開発者のトーン。煽らない。誇大表現・収益保証はしない。
- 1投稿は140字目安（長め可だが冗長にしない）。
- パターンを3つ: ①結論ファースト ②困りごと共感型 ③学びの一言型
- ハッシュタグ候補も2〜4個（#Unity #個人開発 など）。
- 記事URLは {URL} のプレースホルダにする。

# 記事の要点
（タイトルと要点を3行ほど貼る）
```

## 11. X投稿前チェックリスト

投稿ボタンを押す前に確認する:

- [ ] 誇大表現・収益保証がない。
- [ ] 記事の内容と告知文がずれていない。
- [ ] URLが正しい（公開済みURLに差し替えた）。
- [ ] 他者を巻き込む表現・引用RTの角が立っていない。
- [ ] 秘密情報・未公開情報が含まれていない。
- [ ] ハッシュタグが多すぎない（読みにくくない）。
- [ ] **投稿は自分の意思で押す**（自動投稿しない）。

---

## 12. 投稿後に見る数字

数字は「次に何を書くか」の材料。一喜一憂より傾向を見る。

- note: ビュー数 / スキ数 / 読了の手応え / フォロー増減。
- X: インプレッション / いいね / リポスト / プロフィールクリック / リンククリック。
- どの記事・どの切り口が伸びたか（テーマ別の反応の差）。
- コメント・引用での質問や指摘（次のネタの種）。

※ 数字は環境や運次第で大きくぶれる。**伸びなくても内容の価値が否定されたわけではない。**

---

## 13. 次の記事ネタにする基準

次に書く題材を選ぶときの目安:

- 自分が**実際にハマって時間を溶かした**こと（共感されやすい）。
- 解決して**再現性のある手順・テンプレ**にできること。
- 過去記事で**反応が良かった切り口**の続き・深掘り。
- 読者から**質問が来た**こと（需要が見えている）。
- 一本の記事として**無料でも完結して役に立つ**こと。

逆に避ける: 裏取りできない話 / 誰かを叩くだけの話 / 自慢だけで読者の得がない話。

---

## 14. 有料テンプレ集へ発展させる判断基準

無料記事の延長で有料コンテンツを作るかどうかの目安。**焦って有料化しない。**

- 同じテーマの無料記事が**複数本たまり、反応も確認できている**。
- 無料部分だけでも**十分役に立つ**状態で、有料は「さらに深く・楽に」の位置づけにできる。
- 有料にする中身が**自分の実体験ベースで、コピペで使える具体物**（テンプレ・チェックリスト等）。
- 「無料で十分」と思われない程度の**追加価値**を説明できる。
- 値付け・販売開始は**人間が決める**（AIに決めさせない）。第4章参照。

> 収益は保証できない。あくまで「価値を出した結果として導線がある」程度に捉える。

---

## 15. やってはいけないこと

この運用での禁止事項。明文化しておく。

- **noteやXへAIが勝手に投稿すること**（人間確認を飛ばす自動投稿は禁止）。
- **公開・販売・git操作をAIの判断だけで実行すること。**
- **収益保証・誇大表現を書くこと**（「必ず稼げる」「完全自動」「絶対防げる」等）。
- **裏取りしていない事実・数値・捏造エピソードを載せること。**
- **他者・他サービスを不当に貶める表現。**
- **秘密情報（APIキー、未公開情報、個人情報）の混入。**
- **専門家を装って断定すること**（あくまで個人開発者の体験談）。
