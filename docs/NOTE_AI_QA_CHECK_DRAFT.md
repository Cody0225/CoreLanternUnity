# AIの「直しました」を信じてはいけない：成果物QAの作り方

## はじめに

Unityで個人ゲームを作りながら、Claude Code や Codex、ChatGPT を使っています。

AIに作業を任せていると、よくこう報告されます。「直しました」「修正しました」「対応しました」。
最初のころは、その言葉をそのまま信じていました。でも、実際に中身を見てみると——直っていない。あるいは、指摘したのとは別のところをいじって「直したことにしている」。そういう場面に、何度か出くわしました。

これは「AIが嘘つきだ」という話ではありません。AIは悪気なく、「自分としては作業した」と思って報告してきます。ただ、こちらが求めていた直し方と、AIがやった作業がズレていることがある。そのズレに気づかず受け取ると、時間も手間も無駄になります。

この記事は、AIに成果物を直してもらうときに、「本当に直ったか」を確認するための自分なりのルールをまとめたものです。
専門家として書いているわけではなく、個人開発でつまずいた経験から作った、ふだん使いの確認手順です。エンジニアでない人にも分かるように書きました。

なお、これで失敗が完全になくなるわけではありません。でも、「直しました」をうのみにするよりは、だいぶ手戻りが減りました。

---

## AIの「直しました」をそのまま信じると危ない理由

なぜ、報告をそのまま信じると危ないのか。理由はシンプルです。

- **「作業した」と「直った」は別物。**
  AIは何かしら手を動かすと「やりました」と言いがちです。でも、その作業が問題を解決したかどうかは、別の話です。動かした＝直った、ではありません。

- **指摘とズレた直し方をすることがある。**
  「Aがおかしい」と言ったのに、Aではなく近くのBをいじっていたり、見た目の言葉だけ変えて中身は同じ、ということがあります。本人（AI）は直したつもりなので、報告は自信たっぷりです。

- **報告の自信と、実際の品質は比例しない。**
  「完璧です」「修正完了しました」と言われても、それは実際に良くなった保証にはなりません。トーンの強さと中身は別、と割り切る必要があります。

- **確認をサボると、後でまとめて返ってくる。**
  その場で確認しないと、後から「あれ、結局直ってない」と気づき、もう一度やり直すことになります。早めに見たほうが、結局ラクです。

ようするに、**判断の基準を「AIが何と言ったか」ではなく「実際にどうなったか」に置く**。これだけで、かなり防げます。

---

## 実際に困ったこと

具体的に、自分が「やられたな」と思った例を挙げます。どれも個人開発でAIに素材やコードを直してもらう中で起きたことです。

### 1. 指摘した箇所が、まったく変わっていなかった

「ここの動きがおかしい」と伝えて、「直しました」と返ってきた。
でも見比べると、指摘した部分は前とまったく同じ。別のファイルを作り直しただけで、肝心のところは手つかずでした。

### 2. 中身ではなく、呼び方だけ変えていた

「この表示が変だ」と言ったら、表示そのものではなく、ラベル（名前）を別の言葉に変えて「直しました」と報告された。
問題は見た目のほうなのに、言葉を言い換えただけ。これは直したことになりません。

### 3. 作り直したら、前より悪くなっていた

「ちょっと直して」とお願いしたら、まるごと作り直してきて、良かったところまで一緒に消えていた。
部分的な修正のつもりが、全体が劣化して返ってくる。これも地味に困りました。

### 4. 「できました」だけで、何をしたか分からない

報告が「対応しました！」の一行だけ。何を、どこを、どう変えたのかが書いていない。
結局こちらが全部見比べる羽目になり、「これなら最初から自分で確認の指示を出しておけば」と思いました。

---

これらに共通するのは、**AIの報告を入り口にして判断してしまった**ことです。
入り口を「実際の成果物」に変えるだけで、上のほとんどは防げます。次から、その具体的なやり方です。

---

## Before / After を出させる

一番効くのが、これです。**「直す前」と「直した後」を並べて出してもらう**こと。

直したと言うなら、

- 直す前はどうだったか
- 今回どこを変えたか
- 直した後はどうなったか

の3点をセットで出してもらいます。並べて見れば、「本当に変わったのか」「変わったのは指摘した箇所か」が一目で分かります。

ポイントは、**変化が見える形で出させる**ことです。画像なら前後の画像、文章やデータなら「ここがこう変わった」という差分。
逆に、前後を並べられない・違いを説明できない場合は、たいてい「実は直っていない」サインです。「前と何が変わりましたか？」と一言聞くだけで、ごまかしに気づけることがあります。

> コツ: 「直しました」と言われたら、反射的に「Before / Afterを見せて」と返す。これを口ぐせにするだけで品質が上がります。

---

## 成功条件を先に決める

直してもらう前に、**「どうなったら直ったと言えるか」を先に決めて伝えておく**ことも大事です。

これがないと、AIは「自分なりのゴール」で作業して、「できました」と言ってきます。そのゴールがこちらの期待とズレていると、すれ違いが起きます。

たとえば素材なら、

- 「キャラの見た目（色・形）は今のまま維持する」
- 「動きのこの部分だけ自然にする」
- 「他のところは変えない」

のように、**満たすべき条件**と**変えてほしくない範囲**を先に言葉にしておきます。

成功条件を先に決めておくと、後から「これは直ったと言える？」を、感覚ではなく**チェック項目で判断**できます。AI自身にも「この条件を満たしたか確認してから報告して」と頼めるので、雑な報告が減ります。

---

## 何を直したかを報告させる

「直しました」だけで終わらせず、**何を・どこを・どう変えたかを具体的に報告させる**ようにします。

報告に入れてほしいのは、だいたいこのあたりです。

- 直した箇所（どのファイルの、どの部分か）
- 具体的に何を変えたか
- 指摘した問題が解決したと言える理由
- まだ残っている不安な点があれば、それも正直に

特に効くのが、最後の**「不安な点を正直に書いて」**という一言です。AIは黙って自信満々に出してくることがあるので、自己申告の余地を作っておくと、あやしい箇所を先に拾えることがあります。

また、「作り直しただけ」「呼び方を変えただけ」のときは、それを**そのまま書いてもらう**ようにします。「今回は新規に作り直しただけで、指摘箇所の修正はしていません」と書いてもらえれば、こちらも誤解しません。

---

## 2回失敗したら止めるルール

もうひとつ、自分で決めているのが、**同じ問題で2回直しに失敗したら、いったん止める**というルールです。

AIに「もう一回」「まだ違う」を繰り返していると、微妙な成果物が何度も出てきて、時間も（AIの場合は）使用量も、どんどん消費します。3回目、4回目とズルズルいくと、消耗するわりに良くなりません。

なので、

- 同じ指摘で2回直しても直らなかったら、そこで生成・修正を止める
- いったん「何がうまくいっていないか」を整理する
- アプローチを変える（頼み方を変える、分割する、自分で手を入れる、など）

という切り替えをします。

「止める」のは負けではありません。**ダメなやり方を繰り返さないための、前向きな撤退**です。2回でいったん区切る、と決めておくだけで、無駄な往復がかなり減りました。

## コピペ用QAテンプレ

ここまでの内容を、AIに渡せるテンプレにまとめました。コピペして使えます。

直しを依頼するときに、最初にこれを付けておきます。

```text
【修正の依頼／確認ルールつき】

直してほしいのは次の点です。
- （直してほしいことを具体的に書く）

成功条件（これを満たしたら「直った」とします）:
- （満たすべき条件）
- （変えてほしくない範囲。例: 良かった部分は維持する）

報告のしかた:
1. Before / After を並べて見せてください（変化が分かる形で）。
2. 何を・どこを・どう変えたかを具体的に書いてください。
3. 指摘した問題が解決したと言える理由を書いてください。
4. まだ残る不安な点があれば、正直に書いてください。
5. もし「作り直しただけ」「呼び方を変えただけ」なら、そう正直に書いてください
   （それは修正とは扱いません）。

注意:
- 「直しました」だけの報告は受け取れません。上の形で出してください。
- 同じ問題で2回直しても直らない場合は、無理に続けず、いったん止めて
  「何がうまくいっていないか」を整理して相談してください。
```

確認する側（自分）のチェックリストとしても使えます。

```text
【受け取る前の自己チェック】

- [ ] Before / After を自分の目で見比べた。
- [ ] 変わったのは、指摘した箇所か（別の場所ではないか）。
- [ ] 呼び方や言葉を変えただけになっていないか。
- [ ] 良かった部分が、巻き込まれて劣化していないか。
- [ ] 先に決めた成功条件を満たしているか。
- [ ] 同じ問題で直しが2回続けて失敗していないか（していたら止める）。
```

## まとめ

- AIの「直しました」は、**作業した報告であって、直った保証ではない**。
- 判断の基準は「AIが何と言ったか」ではなく「実際にどうなったか」に置く。
- 効く順に、こんな確認をする:
  1. **Before / After を並べて出させる**（一番効く）
  2. **成功条件を先に決めておく**
  3. **何を・どこを・どう変えたかを報告させる**（不安な点も正直に）
  4. **同じ問題で2回失敗したら、いったん止める**
- それでも完璧ではないので、最後は**自分の目で見比べる**のが結局いちばん確実。

AIに直してもらうこと自体は、すごく便利です。やめる必要はまったくありません。
ただ、「直しました」をそのまま信じるのではなく、**実物を見て自分で判断する**。その一手間を挟むだけで、無駄な往復がぐっと減りました。

この「AIに何をどう確認するか」という話は、修正作業にかぎらず応用がきくテーマだと思っています。別の場面についても、おいおい書いていくつもりです。
