# Claude Code / CodexにUnityプロジェクトを壊されないための依頼テンプレを作った

## はじめに

最近、Claude Code や Codex、ChatGPT を使いながら個人でUnityゲームを作っています。

最初は「AIに任せれば開発が爆速になる」とワクワクしていたんですが、実際に使ってみると、便利な反面けっこう普通にミスります。
頼んでいないファイルを書き換えたり、勝手に画像を生成し始めたり、「終わりました！」と言うわりに何をやったのか分からなかったり。

正直、AIツールは強力です。それは間違いない。
ただ「賢いから安心して全部任せられる」かというと、そうではありませんでした。むしろ**雑に頼むと雑に壊す**。人間の新人と同じで、最初の指示が曖昧だと事故ります。

この記事は、AI開発の専門家として書いているわけではありません。
ただの個人ゲーム開発者が、何度も小さい事故を起こした結果、「最初にこう頼んでおけば被害が減った」という指示テンプレを自分用にまとめたものです。

完全に事故を防げる魔法ではありません。でも、何も指定しないよりは確実にマシになりました。同じようにUnityを個人開発している人の参考になればと思って公開します。

---

## AI開発で実際に困ったこと

まず、自分が実際にやられたことを正直に並べます。「あるある」と思う人がいるはず。

### 1. 勝手に作業を進める

「このバグの原因を調べて」と聞いただけなのに、調べるどころか勝手にコードを書き換えて「直しました」と言ってくる。
こちらはまだ原因の見立てを聞きたかっただけなのに、いつの間にか差分ができている。それが正しい修正ならまだしも、見当違いの場所をいじっていることもある。

### 2. 触ってほしくないファイルに触る

これが一番こわい。
うちのプロジェクトには、何千行もある巨大なメインスクリプトがあります。これを一度壊すと復旧が本当に大変です。
それなのに「ちょっとした調整」のつもりが、その巨大ファイルに手が伸びていたりする。AIは「関連してそうなファイル」を遠慮なく開いて編集してくるので、聖域を伝えておかないと普通に踏みます。

### 3. 頼んでいないのに画像を生成される

「アイコンのことで相談」と言っただけで、いきなり画像を生成し始めることがありました。
こちらは方針を相談したかっただけ。生成は時間もかかるし、トークンも食うし、そもそも要らない。「作って」と言うまで作らないでほしい。

### 4. 完了報告が雑

「対応しました！」だけで終わる。
何のファイルを、どこを、なぜ変えたのかが書いていない。結局こちらが差分を全部追いかけて確認することになり、「自分でやったほうが早かったのでは」となる。

### 5. 文字化け・エンコーディング事故

これはツールというより環境の問題も絡みますが、日本語コメントの入ったファイルを別の方法で書き戻したら、盛大に文字化けしたことがあります。
一括置換系のコマンドでファイル全体を書き戻すような操作は、地雷を踏みやすい。

---

こうした事故の共通点は、**「AIが悪い」というより「指示が曖昧だった」** ことです。
人間の外注でも、最初に「これは触らないで」「勝手に進めないで」「報告はこの形で」と伝えますよね。AIにも同じことを最初に言えばいい。それだけで被害がかなり減りました。

---

## 最初に指定すべき安全ルール

セッションの一番最初、もしくはプロジェクトの設定ファイル（`CLAUDE.md` など）に、次のようなルールを書いておくと安定します。
これは「お願い」ではなく「ルール」として最初に渡すのがコツです。

```
## 作業ルール（最初に必ず読むこと）

1. 勝手にコードを変更しない。
   - まず「何をどう変えるか」の方針を説明し、私のOKが出てから編集する。
   - 「調べて」「見て」と言われたときは、調べるだけ。編集はしない。

2. 指定したファイル以外は変更しない。
   - 変更してよいファイルは、私が明示したものだけ。
   - 関連していそうでも、勝手に他のファイルを開いて直さない。

3. 画像・音声などの素材を勝手に生成しない。
   - 「生成して」と明示的に言うまで作らない。
   - 相談・方針の確認の段階では作らない。

4. 不確実なときは手を止めて質問する。
   - 解釈が複数ありうるときは、勝手に決めず確認する。

5. 完了報告は決まった形式で出す（後述）。
```

ポイントは、**「やっていいこと」より「やってはいけないこと」を先に書く**ことです。
AIは放っておくと前のめりに進みます。ブレーキを最初に握らせるイメージです。

---

## 変更禁止リストの例

特に大事なのが「これは絶対に触らないで」という**変更禁止リスト**です。
プロジェクトには、壊れると致命的なファイルや、自動生成されるべきファイルがあります。それを名指しで守ります。

```
## 変更禁止リスト（このファイル/フォルダは編集しないこと）

- Assets/Scripts/（巨大なメインスクリプト）
  → 触る必要があるときは、必ず事前に私へ確認する。勝手に編集しない。

- *.meta ファイル
  → Unityが管理するので手動で書き換えない。

- ProjectSettings/ 配下
  → プロジェクト全体に影響するため、勝手に変更しない。

- .git/、Library/、Temp/、obj/
  → 自動生成・管理領域。手を出さない。

- *.unity（シーンファイル）
  → 壊れると復旧が大変。テキスト編集での書き換えはしない。

## 編集してよい範囲
- 今回の依頼で私が指定したファイルのみ。
- それ以外を変える必要が出たら、先に理由を説明して確認を取る。
```

リストの中身は人によって違います。
「自分が壊されたら泣くファイルはどれか」を一度書き出しておくと、毎回貼り付けるだけで済みます。

補足として、**ファイル全体を書き戻すような一括操作（一括置換コマンドでの上書きなど）も禁止**にしておくと、文字化け事故を減らせます。「編集は差分（部分置換）で行うこと」と一文足しておくと安心です。

## レビューだけ依頼するテンプレ

「直してほしい」のではなく「まず見てほしい」ときのテンプレです。
これを使うと、勝手に編集される事故がかなり減ります。

```
【レビューのみ依頼／編集禁止】

以下のファイルを読んで、レビューだけしてください。
コードの変更は一切しないでください。

対象ファイル:
- （ファイルパスを書く）

見てほしい観点:
- バグになりそうな箇所
- パフォーマンス上の懸念
- 命名や構造で分かりにくいところ

出力してほしい形式:
- 指摘ごとに「ファイル名:行番号」「何が問題か」「どう直す案か」
- 実際の修正コードは出さなくてよい（まず方針だけ知りたい）

繰り返します。今回は編集しないでください。提案だけお願いします。
```

「編集しないで」を**最初と最後の両方**に書くのがコツです。
長い指示の途中の一文は、わりと無視されます。挟み込むと効きます。

## 作業完了報告テンプレ

実際に作業をお願いしたあと、「終わりました！」だけで済まされないように、報告フォーマットを最初に指定しておきます。

```
作業が終わったら、以下の形式で報告してください。

## 完了報告

### やったこと
- （何を実現したか、1〜3行で）

### 変更したファイル
- ファイルパス: 変更内容の要約
- （変更したものを全部列挙する）

### 触っていないもの
- 変更禁止リストのファイルに触れていないことを明記
- 指定外のファイルを変更していないことを明記

### 確認してほしいこと
- 私がUnity側で目視チェックすべき点
- 動作確認の手順（あれば）

### 不安な点・未解決の点
- 自信がない箇所があれば正直に書く
```

特に「**触っていないもの**」をわざわざ報告させるのが効きます。
これを書かせると、AI自身も「禁止リストを守ったか」を最後に自己チェックするので、踏み抜きに気づきやすくなります。

「不安な点を正直に書く」欄も地味に重要です。AIは黙って自信満々に間違えることがあるので、自己申告の余地を残しておくと拾えることがあります。

## 注意書き

正直なところを書いておきます。

- **これらのテンプレを使っても、事故が完全になくなるわけではありません。**
  AIはルールを無視することがあります。長い会話の途中で最初のルールを忘れることもあります。「完全に防げる」とは言えません。

- **最終確認は必ず自分でやってください。**
  差分（変更点）を自分の目で確認する習慣は、テンプレを使っても省略できません。むしろテンプレは「自分で確認しやすくするための下準備」です。

- **こまめにコミットしてください。**
  一番効くのは、実はテンプレより `git commit` です。事故ってもすぐ戻せる状態を保っておけば、被害は最小で済みます。AIに任せる前に区切りでコミット、これだけで安心感がまるで違います。

- **ツールやバージョンで挙動は変わります。**
  ここに書いたのはあくまで「私の環境で効いた」話です。あなたの環境では別の工夫が要るかもしれません。

AIツールは便利です。使うのをやめろという話ではまったくありません。
ただ「賢い新人に初日から大事な作業を任せる」くらいの警戒心は持っておいたほうがいい、という温度感です。

## まとめ

- AIコーディング支援ツールは強力だけど、**雑に頼むと雑に壊す**。
- 最初に「やってはいけないこと」を渡すと、事故がかなり減る。
- 特に効いたのは次の4つ:
  1. **勝手に編集させない**（調べてと頼んだら調べるだけ）
  2. **変更禁止リストを名指しで渡す**
  3. **レビューだけ依頼するときは「編集禁止」を最初と最後に書く**
  4. **完了報告フォーマットを決めて「触っていないもの」も報告させる**
- それでも完璧ではないので、**自分で差分確認＋こまめにコミット**が最後の砦。

ここまでは、コピペしてすぐ使える基本テンプレでした。
実際に運用していると、「ファイル分割するときの頼み方」「巨大ファイルを安全に編集してもらう手順」「複数のAIツールを同時に使うときの衝突回避」など、もう一段細かいテンプレが欲しくなってきます。

そのあたりの、自分が事故を重ねて作り込んだ実践テンプレ集は、別途まとめる予定です。
まずはこの記事の基本セットを自分のプロジェクトに貼り付けて、効果を試してみてください。それだけでもだいぶ平和になるはずです。
