# Claude Codeに勝手にcommit/pushされないためのgit操作ルールを作った

## はじめに

Unityで個人ゲームを作りながら、Claude Code や Codex、ChatGPT を使っています。

**この記事はgitに詳しくない人にも向けて書いています。** 「AIでゲームやアプリを作ってみたい」という、エンジニアではない人にも分かるように、専門用語にはそのつどかんたんな補足を入れていきます。すでにgitを使っている人は、補足は読み飛ばして大丈夫です。

AIにコードや文章の下書きを任せるのはかなり便利です。ただ、使っていてひとつ「これは気をつけないとな」と思ったことがあります。

**git操作（commit / push など）を、こちらが頼んでいないのにAIが進めようとすることがある。**

先日も、自分は「今回はgit操作しないで」と最初に伝えていました。それなのに、作業の途中で出てくる自動チェック（コミット忘れを知らせてくる仕組み）をきっかけに、AIが「じゃあコミットしておきますね」という流れに入りかけたことがありました。

これは「AIが悪い」というより、指示の優先順位を決めていなかった自分の問題でもあります。
そこで、git操作だけは特別扱いして、勝手に実行されないためのルールを自分用に作りました。同じようにAIツールで個人開発している人の参考になればと思って書いておきます。

なお、これで事故が完全になくなるとは言いません。AIはルールを忘れることもあります。あくまで「何も決めていないよりは落ち着く」程度の話として読んでください。

## まず、出てくる言葉のかんたん補足

この記事には git（ギット）という、変更履歴を管理する仕組みの言葉が出てきます。最初に、ざっくりイメージだけ持っておくと読みやすいです。正確な定義というより「だいたいこんな感じ」という説明です。

- **git（ギット）** … ファイルの変更履歴を記録しておく仕組み。ゲームの「セーブデータ管理」に近いイメージ。
- **commit（コミット）** … 今の状態を記録する**作業のセーブポイント**を作ること。「ここまでできた」と区切って保存する感じ。
- **push（プッシュ）** … 手元の記録を**GitHub（ネット上の保管場所）にアップロードすること**。自分のPCの外に出す操作。
- **diff（ディフ／差分）** … **どこが変わったかの差分**。前の状態と比べて「ここが増えた・消えた」を見せてくれるもの。
- **PR（プルリクエスト）** … **変更を確認して取り込むための申請**。「この変更を入れていいですか？」とお伺いを立てる仕組み。
- **GitHub（ギットハブ）** … その記録やコードをネット上に置いて共有できるサービス。

ものすごくざっくり言うと、**commit＝セーブ、push＝ネットにアップロード**。この2つだけ押さえておけば、この記事の話はだいたい追えます。

## 実際に困ったこと

git まわりで「ヒヤッとした」「実際にやられた」ことを正直に並べます。

### 1. 頼んでいないのにコミットしようとする

「ファイルの中身を見せて」「下書きだけ作って」と頼んだだけなのに、作業のついでにコミット（セーブポイントを作ること）まで進めようとする。
こちらはまだ内容を確認したかっただけ。自分で「どこが変わったか（差分）」を見る前に記録に積まれてしまうのは困ります。

### 2. 自動チェックを理由に push まで進みかける

エディタやCLIには、「コミットされていない変更がありますよ」と知らせてくれる仕組みがあります。これ自体は親切な機能です。
ただ、その通知をAIが「じゃあコミット＆pushしておきます」と受け取ってしまうと、こちらの「今回はやらないで」という指示を上書きしてしまう。**通知は通知であって、実行の許可ではない**のに、そこが混ざることがありました。

### 3. 複数ファイルをまとめて記録対象にしてしまう

セーブする前には、「どのファイルを今回の記録に含めるか」を選ぶ工程があります（これを add／ステージと呼びます。レジに通すカゴに入れるイメージ）。
ここで「このファイルだけ」と言ったのに、`git add .`（＝今ある変更を全部まとめてカゴに入れる操作）のような形で、関係ないファイルまで巻き込んでしまうことがあります。
Unityだと自動生成ファイルや設定ファイルが大量にあるので、まとめて入れられると余計なものまで混ざりやすいです。

### 4. 確認なしに push される

手元（自分のPC）で止めておきたかった変更が、いつの間にかネット上（GitHub）に上がっている。
push はその「ネットにアップロードする」操作なので、いったん出すと取り消しにくい。ヒヤッとする度合いが一番大きいのがこれでした。

---

これらに共通するのは、**git操作を他の作業と同じノリで進められてしまう**ことです。
ファイルの編集はやり直しがききますが、git操作は影響範囲が広く、人を巻き込みます。だから特別扱いが要る、という考えに至りました。

## なぜgit操作は危ないか

そもそも、なぜgit操作だけ慎重になるのか。理由を整理しておきます。

- **push（ネットへのアップロード）は外に出る操作。**
  GitHub に上げた時点で、他の人が見られる・取り込める状態になります。間違いを完全に「なかったこと」にはしにくい。

- **記録（履歴）は残る。**
  雑なセーブや、入れたくなかったファイルを含んだまま記録すると、それが履歴として残り続けます。後から見返したときに分かりにくくなります。

- **巻き込み範囲が広い。**
  「全部まとめてカゴに入れる」ような操作は、意図しないファイルまで一緒に扱ってしまうことがあります。Unityは自動で作られるファイルが多く、特に混ざりやすい。

- **「戻す」操作のほうがむしろ難しい。**
  間違ったセーブやアップロードを直すには、gitの取り消し操作が必要です。これは慣れていないと、直そうとして余計にこんがらがりがちです。

- **確認のコストが後払いになる。**
  勝手に進められると、結局あとから「何が記録されたのか」を自分で追いかけることになります。先に確認したほうが、トータルではラクです。

ふつうのファイル編集なら「あ、間違えた」で書き直せば済みます。それがgit操作だと「どうやって戻すんだっけ…」になりやすい。この差が、慎重になる理由です。

## AIに許可してよいgit操作 / 許可しないgit操作

全部禁止する必要はありません。「見るだけ」の操作は安全なので任せやすい。「変える・外に出す」操作は人間が確認する。そんな線引きにしています。

### 任せてもいい（見るだけ・確認するだけの操作）

状態を「変えない」、ただ見るだけの操作です。これらは安全なので、むしろ積極的にやってもらって状況を教えてもらいます。

- `git status`（今どうなっているかの確認）
- `git diff`（どこが変わったか＝差分の確認）
- `git log`（これまでのセーブ履歴の確認）
- `git branch`（作業の枝分かれ＝ブランチの一覧確認）
- どのファイルが変わったか、何が混ざりそうかを**報告してもらう**こと

### 人間が確認してから（変える・外に出す操作）

ここからは状態を変えたり、ネットに出したりする操作です。「やっていい？」と一度止まってもらい、実行は人間がOKを出してから、もしくは人間自身が行います。

- `git add`（セーブに含めるファイルを選ぶ操作。特に「全部まとめて」は要注意）
- `git commit`（セーブポイントを作る）
- `git push`（ネットにアップロードする）
- `git merge` / `git rebase`（記録のつなぎ方を変える操作。やや上級者向け）
- ブランチの削除や、強制的に上書きする系の操作

### 原則やらせない

- **PR（プルリクエスト＝変更を取り込むための申請）の作成・マージ。** 公開・共有につながる操作なので、人間が判断します。
- **`--force`（強制）系のpush。** 文字どおり強引に上書きする操作で、間違えたときの被害が大きいです。

線引きの基準はシンプルで、**「やり直しがきくか」「外に出るか」**です。見るだけなら任せる、変える・外に出すなら人間が確認する、という分け方です。

## git操作を依頼するときの安全テンプレ

実際にAIへ頼むときに使っているテンプレです。コピペして使えます。

まず、git操作をしてほしくないとき:

```text
【git操作 禁止】
今回の作業では git 操作を一切しないでください。
- git add / commit / push / PR作成 はしないでください。
- 変更はファイルの編集だけにとどめてください。
- 自動チェックやフックで「コミットして」と出ても、私の確認なしに実行しないでください。
作業が終わったら「変更したファイル一覧」だけ報告してください。コミットは私がやります。
```

次に、git操作を頼みたいとき（でも勝手に進めてほしくないとき）:

```text
【git操作 依頼／ただし確認してから】
以下の手順でお願いします。

1. まず git status と git diff を見せてください（まだ何も変更しない）。
2. 何を、どのファイルだけ commit するつもりか、先に説明してください。
3. 私がOKと言ってから、指定したファイルだけ add → commit してください。
   - git add . は使わないでください。ファイルを名指しで add してください。
4. push する前に、もう一度確認を取ってください。

commit message案も先に出してくれて構いませんが、実行は私のOKの後で。
```

ポイントは、**「確認してから」を最初と最後に書く**ことと、**add するファイルを名指しさせる**ことです。

## Stop hookや自動チェックよりユーザー指示を優先させるルール

ここが今回いちばん書きたかったところです。

エディタやCLIには、「コミットされていない変更があります」と教えてくれる仕組み（いわゆるフックや自動チェック）があります。便利です。でも、これは**「状況のお知らせ」であって「実行していい合図」ではありません。**

自分が決めたルールはこうです。

- **自動チェックの通知は、あくまで情報。** それを見て実行するかどうかは人間が決める。
- **「git操作しないで」という私の指示は、自動チェックより優先。** 通知が出ても、私が止めている限りAIは実行しない。
- **通知が出たら、AIは実行ではなく報告する。** 「未コミットの変更がありますが、どうしますか？」と聞いてくるのが正解。勝手に commit しに行くのは違う。
- **迷ったら止まって聞く。** 解釈が割れそうなときは、進めるより確認を取るほうを選ぶ。

要するに、**人間の指示 > 自動チェックの通知**という優先順位をはっきりさせておく、ということです。
これを最初に伝えておくと、「フックが言ってたので…」という形で勝手に進む流れを減らせます（完全には防げませんが、減らせます）。

依頼文に一行足すならこんな感じです。

```text
フックや自動チェックの通知より、私の指示を優先してください。
通知が出ても、私が「やらないで」と言った操作は実行せず、報告だけしてください。
```

## commit前チェックリスト

実際にセーブ（コミット）する前に、人間（自分）が確認する項目です。AIに任せた場合でも、最後はこれを自分で見ます。

- [ ] そもそも今セーブしていいタイミングか（人間が決めた）。
- [ ] 変更内容（差分）を自分の目で見た（`git status` / `git diff`）。
- [ ] セーブに含めたのは意図したファイルだけ（「全部まとめて」で余計なものを巻き込んでいない）。
- [ ] 自動生成ファイル・設定ファイル・秘密情報（パスワードやAPIキーなど）が混ざっていない。
- [ ] セーブにつける説明文（コミットメッセージ）が、中身と合っている。
- [ ] ネットへのアップロード（push）は別判断（やってよいか、改めて確認した）。
- [ ] PR（取り込み申請）は作らない（必要なら別途、人間が判断する）。
- [ ] **最終的に実行ボタンを押すのは自分**（AIに急かされて押していない）。

## まとめ

- AIツールは便利だけど、**git操作（セーブやアップロード）は影響が大きいので特別扱いする**。
- 危ないのは push（ネットへのアップロード）・履歴の変更・「全部まとめてセーブ」など、「外に出る」「やり直しにくい」操作。
- 線引きは **「見るだけ」は任せる／「変える・外に出す」は人間が確認**。
- **自動チェックの通知は情報であって、実行の許可ではない。** 人間の指示を優先する。
- 依頼するときは「確認してから」を最初と最後に書き、含めるファイルは名指しさせる。
- それでも完璧ではないので、**最後に自分で変更内容（差分）を見てから実行する**のが、結局いちばん効きます。

git操作をAIに一切させない、という話ではありません。確認系は任せて、変更系は人間が握る。それだけで、ヒヤッとする場面はだいぶ減りました。

このあたりの「AIに何を任せて、何を自分で握るか」の線引きは、git以外にも応用がきくテーマだと思っています。別の作業についても、おいおい書いていくつもりです。
