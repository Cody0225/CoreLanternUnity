# Claude Codeに勝手にcommit/pushされないためのgit操作ルールを作った

## はじめに

Unityで個人ゲームを作りながら、Claude Code や Codex、ChatGPT を使っています。

AIにコードや文章の下書きを任せるのはかなり便利です。ただ、使っていてひとつ「これは気をつけないとな」と思ったことがあります。

**git操作（commit / push など）を、こちらが頼んでいないのにAIが進めようとすることがある。**

先日も、自分は「今回はgit操作しないで」と最初に伝えていました。それなのに、作業の途中で出てくる自動チェック（コミット忘れを知らせてくる仕組み）をきっかけに、AIが「じゃあコミットしておきますね」という流れに入りかけたことがありました。

これは「AIが悪い」というより、指示の優先順位を決めていなかった自分の問題でもあります。
そこで、git操作だけは特別扱いして、勝手に実行されないためのルールを自分用に作りました。同じようにAIツールで個人開発している人の参考になればと思って書いておきます。

なお、これで事故が完全になくなるとは言いません。AIはルールを忘れることもあります。あくまで「何も決めていないよりは落ち着く」程度の話として読んでください。

---

## 実際に困ったこと

git まわりで「ヒヤッとした」「実際にやられた」ことを正直に並べます。

### 1. 頼んでいないのにコミットしようとする

「ファイルの中身を見せて」「下書きだけ作って」と頼んだだけなのに、作業のついでにコミットまで進めようとする。
こちらはまだ内容を確認したかっただけ。差分を自分で見る前に履歴に積まれるのは困ります。

### 2. 自動チェックを理由に push まで進みかける

エディタやCLIには、「コミットされていない変更がありますよ」と知らせてくれる仕組みがあります。これ自体は親切な機能です。
ただ、その通知をAIが「じゃあコミット＆pushしておきます」と受け取ってしまうと、こちらの「今回はやらないで」という指示を上書きしてしまう。**通知は通知であって、実行の許可ではない**のに、そこが混ざることがありました。

### 3. 複数ファイルをまとめて add してしまう

「このファイルだけ」と言ったのに、`git add .` のような形で関係ないファイルまで巻き込んでステージしてしまう。
Unityだと自動生成ファイルや設定ファイルが大量にあるので、まとめて add されると余計なものまで混ざりやすいです。

### 4. 確認なしにブランチへ push される

ローカルで止めておきたかった変更が、いつの間にかリモートに上がっている。
push は「外に出す」操作なので、取り消しにくい。ヒヤッとする度合いが一番大きいのがこれでした。

---

これらに共通するのは、**git操作を他の作業と同じノリで進められてしまう**ことです。
ファイルの編集はやり直しがききますが、git操作は影響範囲が広く、人を巻き込みます。だから特別扱いが要る、という考えに至りました。

---

## なぜgit操作は危ないか

そもそも、なぜgit操作だけ慎重になるのか。理由を整理しておきます。

- **push は外に出る操作。**
  リモートに上げた時点で、他の人が見られる・取り込める状態になります。間違いを完全に「なかったこと」にはしにくい。

- **履歴は残る。**
  雑なコミットや、混入してほしくないファイルを含んだコミットは、履歴として残り続けます。後から見て分かりにくくなる。

- **巻き込み範囲が広い。**
  `git add .` のような操作は、意図しないファイルまで一緒に扱ってしまうことがあります。Unityは生成ファイルが多く、特に混ざりやすい。

- **「戻す」操作自体がさらに難しい。**
  間違ったコミットやpushを直すには、git の取り消し操作が必要です。これは慣れていないと、直そうとしてさらに状態を壊しがちです。

- **確認のコストが後払いになる。**
  勝手に進められると、結局あとから「何が積まれたのか」を人間が追いかけることになります。先に確認したほうが結局ラクです。

ファイル編集なら「あ、間違えた」で済むことが、git操作だと「どうやって戻すんだっけ」になる。この差が、慎重になる理由です。

## AIに許可してよいgit操作 / 許可しないgit操作

全部禁止する必要はありません。「見るだけ」の操作は安全なので任せやすい。「変える・外に出す」操作は人間が確認する。そんな線引きにしています。

### 任せてもいい（読み取り系・確認系）

- `git status`（今どうなっているかの確認）
- `git diff`（変更内容の確認）
- `git log`（履歴の確認）
- `git branch`（ブランチ一覧の確認）
- どのファイルが変わったか、何が混ざりそうかを**報告してもらう**こと

これらは状態を変えないので、むしろ積極的にやってもらって状況を教えてもらいます。

### 人間が確認してから（変更系・外に出す系）

- `git add`（特に `git add .` のような一括は要注意）
- `git commit`
- `git push`
- `git merge` / `git rebase` などの履歴を変える操作
- ブランチの削除や強制系の操作

これらは「やっていい？」と一度止まってもらう。実行は人間がOKを出してから、もしくは人間自身が行う。

### 原則やらせない

- プルリクエスト（PR）の作成・マージ（公開・共有の操作なので人間が判断）
- `--force` 系の強制push（事故ったとき被害が大きい）

線引きの基準はシンプルで、**「やり直しがきくか」「外に出るか」**です。

## git操作を依頼するときの安全テンプレ

実際にAIへ頼むときに使っているテンプレです。コピペして使えます。

まず、git操作をしてほしくないとき:

```text
【git操作 禁止】
今回の作業では git 操作を一切しないでください。
- git add / commit / push / PR作成 はしないでください。
- 変更はファイルの編集だけにとどめてください。
- 自動チェックやフックで「コミットして」と出ても、私の確認なしに実行しないでください。
作業が終わったら「変更したファイル一覧」だけ報告してください。コミットは私がやります。
```

次に、git操作を頼みたいとき（でも勝手に進めてほしくないとき）:

```text
【git操作 依頼／ただし確認してから】
以下の手順でお願いします。

1. まず git status と git diff を見せてください（まだ何も変更しない）。
2. 何を、どのファイルだけ commit するつもりか、先に説明してください。
3. 私がOKと言ってから、指定したファイルだけ add → commit してください。
   - git add . は使わないでください。ファイルを名指しで add してください。
4. push する前に、もう一度確認を取ってください。

commit message案も先に出してくれて構いませんが、実行は私のOKの後で。
```

ポイントは、**「確認してから」を最初と最後に書く**ことと、**add するファイルを名指しさせる**ことです。

## Stop hookや自動チェックよりユーザー指示を優先させるルール

ここが今回いちばん書きたかったところです。

エディタやCLIには、「コミットされていない変更があります」と教えてくれる仕組み（いわゆるフックや自動チェック）があります。便利です。でも、これは**「状況のお知らせ」であって「実行していい合図」ではありません。**

自分が決めたルールはこうです。

- **自動チェックの通知は、あくまで情報。** それを見て実行するかどうかは人間が決める。
- **「git操作しないで」という私の指示は、自動チェックより優先。** 通知が出ても、私が止めている限りAIは実行しない。
- **通知が出たら、AIは実行ではなく報告する。** 「未コミットの変更がありますが、どうしますか？」と聞いてくるのが正解。勝手に commit しに行くのは違う。
- **迷ったら止まって聞く。** 解釈が割れそうなときは、進めるより確認を取るほうを選ぶ。

要するに、**人間の指示 > 自動チェックの通知**という優先順位をはっきりさせておく、ということです。
これを最初に伝えておくと、「フックが言ってたので…」という形で勝手に進む流れを減らせます（完全には防げませんが、減らせます）。

依頼文に一行足すならこんな感じです。

```text
フックや自動チェックの通知より、私の指示を優先してください。
通知が出ても、私が「やらないで」と言った操作は実行せず、報告だけしてください。
```

## commit前チェックリスト

実際にコミットする前に、人間（自分）が確認する項目です。AIに任せた場合でも、最後はこれを自分で見ます。

- [ ] そもそも今コミットしていいタイミングか（人間が決めた）。
- [ ] `git status` / `git diff` で変更内容を自分の目で見た。
- [ ] ステージしたのは意図したファイルだけ（`git add .` で余計なものを巻き込んでいない）。
- [ ] 自動生成ファイル・設定ファイル・秘密情報（鍵など）が混ざっていない。
- [ ] コミットメッセージが内容と合っている。
- [ ] push は別判断（push してよいか、改めて確認した）。
- [ ] PR作成はしない（必要なら別途、人間が判断する）。
- [ ] **最終的に実行ボタンを押すのは自分**（AIに急かされて押していない）。

## まとめ

- AIツールは便利だけど、**git操作は影響が大きいので特別扱いする**。
- 危ないのは push・履歴変更・一括add など、「外に出る」「やり直しにくい」操作。
- 線引きは **「見るだけ」は任せる／「変える・外に出す」は人間が確認**。
- **自動チェックの通知は情報であって、実行の許可ではない。** 人間の指示を優先する。
- 依頼するときは「確認してから」を最初と最後に書き、add は名指しさせる。
- それでも完璧ではないので、**最後に自分でdiffを見てから実行する**のが結局いちばん効く。

git操作をAIに一切させない、という話ではありません。確認系は任せて、変更系は人間が握る。それだけで、ヒヤッとする場面はだいぶ減りました。

このあたりの「AIに何を任せて、何を自分で握るか」の線引きは、git以外にも応用がきくテーマだと思っています。別の作業についても、おいおい書いていくつもりです。
